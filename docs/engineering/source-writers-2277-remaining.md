## Delta B: revisions:* creation (`createRevision`, resolvers.mutation.session.ts:2067)
Today: snapshot READS (`ctx.db`), unfenced parent `node.upsert` swallowing all errors, then `db.$transaction` (`lockAncestorsForCreate` + `node.create` of `revisions:rev-N`, whole snapshot in `data`). The Agent's system memory is always class `system`: no class condition.
Callers traced: `restoreRevision` (line ~2205) calls `createRevision` as a SEPARATE, COMPLETED step before it opens its own `withIncludeHistoryClientTransaction` (already F-first in #2273). Sequential, never nested, so a fenced `createRevision` cannot hit the nested-fence refusal. No other caller found (grep). publishRevision does not create nodes.
Attach: parent upsert + snapshot reads + create in ONE `withIncludeHistoryTransaction` (F first, then `lockAncestorsForCreate`), READ COMMITTED. Behavior to preserve: authorization stays before the transaction (unchanged); the parent upsert's swallowed error becomes a real rollback only for non-uniqueness failures (a unique-violation on `revisions` is handled by an existence read, not by swallowing everything); rev numbering stays count+1 but is now computed under F so two concurrent creators cannot both pick the same number (today they can, then one hits the loc unique constraint). Rollback: all or nothing, which today the upsert-then-create is not.
Honest limit: F + READ COMMITTED is coherent only against writers that participate; it does not make the snapshot reads coherent against raw non-participating reads/writers (the remaining unfenced source writers are exactly the open rows).
Hold-cost measurement (LOCAL, synthetic, idle single-connection Postgres, one run of 3 calls per size, not a production load test; wall time of the whole createRevision, i.e. an upper bound on the F hold): 10 nodes ~11 ms; 100 ~29 ms; 1,000 ~138 ms; 5,000 ~546 ms (2 KB body each). Roughly 0.1 ms per node. Limits: this blocks every other F participant (compile, other writers) for that long; production memory sizes, concurrency and replica lag are unmeasured operational unknowns; if a system memory can exceed a few thousand nodes the hold needs a cap or a read-outside-F redesign, a decision for Xylon before the production delta.

## A: chat-scope refusal and the two withChatRootLock runners
- Scope gate (`validateChatScopeInvariants`, chat-scope.ts:478): `scope=private` needs a personal/knowledge host, `scope=shared` an app host, a missing scope only personal/knowledge (migration window); group/private always refused. So a SYSTEM-class host is refused by every path that calls it. It is called ONLY by `sendChatMessage` (line 780) and `processChatResponse` (line 1238). `saveChatSummary`, `updateChatTitle` and `deleteChat` do NOT call it (they require current write access and `chatLocFilter` entitlement only). A Channel root created in a system memory is NOT reachable through `updateChatTitle` (the chat lookup answers "not found"; pinned green in `resolvers.sourceWritersRed2277.test.ts`). Whether any chat root can exist in a system host through another path is unproven.
- Allowed producers on a system host: the Channel producers only (createChannel/deleteChannel/createChannelMessage/createTeamChatMessage via `postToChannelRoot` -> `appendChatMessage` -> `withChatRootLock` default runner). The `inTx` runner (`chatWriteTx`) is used by the five chat-session mutations above and reaches a system host only if such a chat root exists; the attach still covers it with the SAME class contract, cost-free outside `system`.
- Prepared-client propagation, both runners: (1) default runner (`db.$transaction`) becomes, for class system, `withIncludeHistoryTransaction`, passing `includeHistoryClient(f)` as `tx`; (2) `chatWriteTx` passes `fence:true` through `withAuthorizedMemoryTx` and its `fn(tx)` receives the SAME fenced client. `ChatRootOpts.inTx` callers therefore never open a second F: when `inTx` is supplied, `withChatRootLock` does not decide a fence itself (the runner owns it); the default runner decides, so there is exactly one F per attempt and the nested-fence guard cannot trip. A pin: `appendChatMessage` supplied a fenced `inTx` must not throw the nested-fence error.

## B: revisions:* creation (authority after the F wait, auto-save semantics, timeout)
- Stale authority: today `requireAgentAccess(ctx, agent, 'ADMIN')` runs on the pooled client BEFORE any wait, so an admin demoted while the writer queues on F would still write. Attach: run the create through `withAuthorizedTx` (agent + org/owner-user anchors, `fence:true`, `authorize` re-running `requireAgentAccess` on the transaction client AFTER the F wait and the anchors, exactly as `restoreRevision`'s own tx does), with the Agent's `systemMemoryId`/owner scope re-read under the lock and a changed scope refused (`FORBIDDEN`, as restoreRevision does).
- restoreRevision auto-save: unchanged order. `createRevision` is awaited and COMPLETES (its tx commits) before restoreRevision opens its own F-first tx; a failure or timeout there throws before the destructive step, so a failed auto-save leaves the memory untouched and no restore happens (today's behavior, kept). The auto-save is its own committed revision (it is not rolled back if the restore later fails); that is current behavior and stays.
- Timeout/rollback: the existing bounded transaction deadline (30 s default for `withAuthorizedTx`/`withIncludeHistoryTransaction`, including the F wait via lock_timeout) with its truthful timeout failure; NO node-count cap and no read-outside-F snapshot (the measurements only informed the cost note above). All-or-nothing: parent, snapshot reads and revision insert roll back together.

## C: reclaim outer authority, row order, cascade set
- Today (resolvers.mutation.agent.ts createAgentCore): org resolved + `requireOrgRole` ADMIN (pooled) -> `agent.findUnique(urn)` -> if tombstone: `ctx.db.agent.delete` (POOLED, autocommit, BEFORE any fence; P2003 mapped to AgentUrnTakenError) -> `withAuthorizedTx(... { fence: true })` creating system memory (+ `reclaimTombstonedMemory` for a stale `-system` memory) and the Agent. The create half is already F-first in the #2273 base; the DELETE is not. The red control proves it: while F is held the old Agent's AgentOrgGrant is already gone.
- Attach: move the tombstone delete INSIDE that fenced transaction, after F, the anchors and the fresh gate, before the stale-system-memory reclaim and the create. Order: F -> org/user anchors (SHARE) -> fresh ADMIN gate -> `agent` tombstone delete (cascade rows) -> stale system-memory reclaim -> memory create -> agent create. P2003 (a Worker casting, Restrict) aborts the interactive transaction; it is mapped to `AgentUrnTakenError` by the existing `.catch` (extended for P2003), and the whole transaction rolls back, so no cascade row is deleted when the refusal fires (today the refusal happens at the statement level).
- Cascade set of `agent.delete` (schema.prisma, relations to Agent): CASCADE: AgentOrgGrant, AgentSubscription, AppAgent (the entitlement/install rows that gate includability), plus AgentMemoryItem, AiServiceConfig, Scope, ChannelReadState (not compile-relevant); SET NULL: Session.agentId; RESTRICT: Worker (the P2003 case). Retained (not cascaded): the system Memory, its Nodes and history.
