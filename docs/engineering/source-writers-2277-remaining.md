## Delta A: Channel roots and everything that writes under them
Admission proven (Anne #31548): the root, the `:messages` parent and a produced chat-message Node all compile by explicit URN; the compile selects `Node.content/revSeq`, not `Node.data`, so a root-metadata edit leaves the selected text/hash unchanged, but a new message Node is independently admitted and emits its body. So the earlier "append exclusion" is withdrawn: appends ARE source writers (new Node).

Producers (traced), all converging on two roots:

Two choke points make this bounded: `withChatRootLock` (src/lib/chatRoot.ts:108) and `ensureChannelWithRoot`/`deleteChannel`.
Attach: (1) `withChatRootLock` default runner: when the chat root's memory is class `system`, run under `withIncludeHistoryTransaction` (READ COMMITTED, as today); F first, then `lockPathForCreateUnder`; class re-read after the path lock (`memories ... FOR SHARE`, compatible with posts' FK KEY SHARE and other SHARE holders; it conflicts only with a class/owner change) and a mismatch retries the whole attempt with a fresh decision, then refuses `NODE_WRITE_CONFLICT`. (2) `chatWriteTx` (the `inTx` runner) passes `fence` on `withAuthorizedMemoryTx` under the same decision/drift contract (shared helper like `sourceFencedMemoryTx`); callers passing a prepared client are not nested. (3) `ensureChannelWithRoot` and `deleteChannel` the same, so the shared ensure/default callers inherit it with no name exemption. Order below F unchanged in every root. Open: chat sessions in a system memory may be refused earlier by the chat-scope invariant (`validateChatScopeInvariants`); the pin will exercise only Channel producers unless the invariant admits a system host, to be confirmed by a red test rather than assumed.

## Delta B: revisions:* creation (`createRevision`, resolvers.mutation.session.ts:2067)
Today: snapshot READS (`ctx.db`), unfenced parent `node.upsert` swallowing all errors, then `db.$transaction` (`lockAncestorsForCreate` + `node.create` of `revisions:rev-N`, whole snapshot in `data`). The Agent's system memory is always class `system`: no class condition.
Callers traced: `restoreRevision` (line ~2205) calls `createRevision` as a SEPARATE, COMPLETED step before it opens its own `withIncludeHistoryClientTransaction` (already F-first in #2273). Sequential, never nested, so a fenced `createRevision` cannot hit the nested-fence refusal. No other caller found (grep). publishRevision does not create nodes.
Attach: parent upsert + snapshot reads + create in ONE `withIncludeHistoryTransaction` (F first, then `lockAncestorsForCreate`), READ COMMITTED. Behavior to preserve: authorization stays before the transaction (unchanged); the parent upsert's swallowed error becomes a real rollback only for non-uniqueness failures (a unique-violation on `revisions` is handled by an existence read, not by swallowing everything); rev numbering stays count+1 but is now computed under F so two concurrent creators cannot both pick the same number (today they can, then one hits the loc unique constraint). Rollback: all or nothing, which today the upsert-then-create is not.
Honest limit: F + READ COMMITTED is coherent only against writers that participate; it does not make the snapshot reads coherent against raw non-participating reads/writers (the remaining unfenced source writers are exactly the open rows).
Hold-cost measurement (LOCAL, synthetic, idle single-connection Postgres, one run of 3 calls per size, not a production load test; wall time of the whole createRevision, i.e. an upper bound on the F hold): 10 nodes ~11 ms; 100 ~29 ms; 1,000 ~138 ms; 5,000 ~546 ms (2 KB body each). Roughly 0.1 ms per node. Limits: this blocks every other F participant (compile, other writers) for that long; production memory sizes, concurrency and replica lag are unmeasured operational unknowns; if a system memory can exceed a few thousand nodes the hold needs a cap or a read-outside-F redesign, a decision for Xylon before the production delta.
