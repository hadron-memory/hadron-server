# Feature Specification: Node `abstractOriginHash` — stale-abstract detection

- **Feature Branch**: `199-abstract-staleness` *(numbering note: the speckit feature-branch script picked `199` because branch `198-ensure-agent-subscription-race` exists from the SC-006 fix; the spec directory uses the canonical sequential number `032` because only `031-node-abstract-field` exists in `specs/`. Branch and dir intentionally diverge — see Assumptions.)*
- **Created**: 2026-05-31
- **Status**: Shipped (2026-05-30; #209 + #210 + #212). Doc drift cleanup bundled in #211.
- **Input**: User description: "Add Node.abstractOriginHash field — stores the hash of the content the abstract was derived from, enabling stale-abstract detection. When `content` is updated without a corresponding `abstract` refresh, the staleness signal (abstractOriginHash != current contentHash) lets read tools mark the preview as stale, lets the validator flag it, and lets the upcoming RAG/vector layer skip or re-queue stale abstracts rather than embedding misleading summaries. Sequenced as a precursor to the RAG follow-up spec — vectorizing stale abstracts is a confidently misleading failure mode that staleness detection prevents."

## Background

Spec 031 (merged 2026-05-30) added `Node.abstract` — a paragraph-length summary of `content`, authored independently (no auto-derivation). The two columns are intentionally separate to give authors control over the summary text. The trade-off: nothing prevents the abstract from going **stale** when content is updated without a corresponding abstract refresh.

Today every consumer that surfaces the abstract — `h-find-nodes` previews, `h-read-node` (via `contentScope`), `h-validate`, and the upcoming RAG / vector-retrieval layer — treats the abstract as authoritative. A reader has no way to distinguish a fresh abstract that accurately summarises current content from a stale abstract that summarises a long-since-edited prior version.

This is acutely dangerous for the **RAG follow-up**: vectorising a stale abstract embeds a confident-but-wrong summary that semantic search will surface as authoritative. The reader trusts the embedding distance metric; they don't know the embedded text no longer matches the node's actual content. Without staleness detection, the RAG layer would amplify the failure mode every time a node's content is edited without its abstract being refreshed.

This spec adds `Node.abstractOriginHash` — a stored hash of the content the abstract was derived from. The hash is maintained automatically on every write surface. Consumers read it alongside `Node.contentHash` and treat divergence as a staleness signal: the abstract may no longer reflect what the content says.

The design is deliberately **passive**: the system observes and reports staleness; it does NOT automatically rewrite or invalidate the abstract. The author (human or agent) remains responsible for refreshing stale abstracts. The follow-up RAG spec will encode the "skip or re-queue" policy on top of the signal this spec exposes.

## User Scenarios & Testing

### User Story 1 — Write paths maintain `abstractOriginHash` correctly so the staleness signal is reliable (Priority: P1)

Every write surface that mutates `abstract` or `content` (MCP `h-add-node` / `h-update-node`, GraphQL `upsertNode`, importer round-trip, version restore) MUST keep `abstractOriginHash` in sync with the intent of the write. Specifically:

- When an author **writes a fresh abstract together with content** (or refreshes the abstract after a content edit), `abstractOriginHash` is set to the hash of the current content. The abstract is fresh; the signal will read "matches" until either side changes.
- When an author **updates only the content** (no abstract update in the same write), `abstractOriginHash` is left untouched. The stored hash now diverges from the new `contentHash`; the signal will read "stale" on the next read.
- When an author **updates only the abstract** (no content change), `abstractOriginHash` is reset to the hash of the current content. The author is explicitly affirming "this abstract matches current content as of this write."
- When the abstract is cleared (`abstract: null`), `abstractOriginHash` is also cleared. No abstract means no staleness signal.

Without US1, US2 and US3 cannot trust the signal: a stale "fresh" reading or a fresh "stale" reading is worse than no signal at all.

**Why this priority**: This is the foundational invariant. Every other story rides on it. Implemented alone, the column is observable (queryable via GraphQL, inspectable in the DB) and the contract is testable — even before any consumer surfaces the staleness signal to users.

**Independent Test**: A test seeds a node with abstract + content, asserts `abstractOriginHash == computeContentHash(content)`. Updates only content; asserts `abstractOriginHash` is unchanged (now stale relative to current content). Refreshes the abstract via `h-update-node`; asserts `abstractOriginHash == computeContentHash(new content)`. Clears the abstract; asserts `abstractOriginHash` is null.

**Acceptance Scenarios**:

1. **Given** an existing memory, **When** an agent calls `h-add-node` with both `abstract` and `content`, **Then** `Node.abstractOriginHash` is set to `computeContentHash(content)`. `Node.contentHash` is NOT touched by this spec — its existing external-producer domain is preserved per data-model.md "What is NOT".
2. **Given** a node with `abstract: "X"`, `content: "Y"`, `abstractOriginHash: computeContentHash("Y")`, **When** an agent calls `h-update-node` with `content: "Y'"` (no abstract field), **Then** `abstractOriginHash` is unchanged (still `computeContentHash("Y")`). On the next read, `computeContentHash(node.content) = computeContentHash("Y'")` disagrees with the stored origin hash — the staleness signal is now armed.
3. **Given** a stale node (origin hash disagrees with `computeContentHash(current content)`), **When** an agent calls `h-update-node` with `abstract: "X'"` (no content field), **Then** `abstractOriginHash` is reset to `computeContentHash(existing.content)` — the author has affirmed the new abstract matches current content.
4. **Given** a node with `abstract: "X"` and a populated `abstractOriginHash`, **When** an agent calls `h-update-node` with `abstract: null` (clearing), **Then** `abstractOriginHash` is also cleared to `null`.
5. **Given** a write to a node where `content` is `null` and `abstract: "X"` is set (the FR-005 fallback case from spec 031), **When** the write completes, **Then** `abstractOriginHash` is `null` (no content to hash; the staleness check naturally short-circuits).
6. **Given** the GraphQL `upsertNode` mutation, **When** the same input shapes from acceptance scenarios 1–5 above are sent, **Then** the resulting `Node.abstractOriginHash` matches the MCP-path expectations byte-for-byte.
7. **Given** the node.yaml importer, **When** a YAML file with both `abstract:` and content body is imported, **Then** `abstractOriginHash` is computed from the imported content (importer treats the YAML as a fresh authored write; round-trip integrity is preserved across export → import).
8. **Given** a `restoreNodeVersion` call, **When** a prior version with both `abstract` and `abstractOriginHash` is restored, **Then** the restored node's `abstractOriginHash` matches the version's stored value (version history captures the hash alongside the abstract).

### User Story 2 — `h-read-node` surfaces a `Source: abstract-stale` marker when the abstract is stale (Priority: P2)

When `h-read-node` is called and the node is stale (`abstract IS NOT NULL` AND `content IS NOT NULL` AND `abstractOriginHash IS NOT NULL` AND `abstractOriginHash != computeContentHash(node.content)`), the meta block carries a `Source: abstract-stale` line. The marker is symmetric in shape to spec 031's `Source: abstract-fallback` marker (same position in the meta block, same parse-friendly format) so a single regex or string check covers both signals. The hash is computed at read time from plaintext content (see FR-008's separation from `Node.contentHash`).

The marker MUST appear under any `contentScope` value that surfaces the abstract — that is, `'abstract'` and `'all'`. Under `contentScope: 'content'` (default), the abstract is not in the response, so the marker is irrelevant and MUST NOT appear (no need to alarm callers about content they aren't reading). The content-fallback case from spec 031 (default scope + content-less node + abstract-having → abstract substituted into body slot) is distinct: there's no content to be stale against, so the `Source: abstract-fallback` marker fires but `Source: abstract-stale` does not.

**Why this priority**: This is the primary user-facing surfacing. An agent reading a node sees the marker and can decide to read the body anyway, refresh the abstract, or treat the abstract with appropriate skepticism. Without US2, the staleness signal exists but only programmatic consumers (RAG layer, future linters) can see it.

**Independent Test**: Seed a node with abstract + content, `abstractOriginHash == computeContentHash(content)`. Read with `contentScope: 'all'`; assert NO `Source: abstract-stale` line. Update only content. Read with `contentScope: 'all'`; assert `Source: abstract-stale` line is present in the meta block (the stored origin hash now disagrees with the read-time recomputed hash). Refresh the abstract. Read again; assert the marker is gone.

**Acceptance Scenarios**:

1. **Given** a fresh node (`abstractOriginHash == computeContentHash(node.content)`, both non-null), **When** `h-read-node` is invoked with `contentScope: 'all'`, **Then** the response is meta block + abstract + `---` + body, with NO `Source: abstract-stale` line in the meta block.
2. **Given** a stale node (`abstractOriginHash != computeContentHash(node.content)`, abstract + content both non-null, hash non-null), **When** `h-read-node` is invoked with `contentScope: 'all'`, **Then** the meta block contains a `Source: abstract-stale` line (positioned consistently with `Source: abstract-fallback` from spec 031 FR-005) and the abstract + content render normally.
3. **Given** a stale node, **When** `h-read-node` is invoked with `contentScope: 'abstract'`, **Then** the meta block contains the `Source: abstract-stale` line and the abstract is returned (no body).
4. **Given** a stale node, **When** `h-read-node` is invoked with `contentScope: 'content'` (default), **Then** the response is byte-identical to a fresh-node default-scope read — NO `Source: abstract-stale` line. The marker only fires when the abstract is actually in the response.
5. **Given** a content-less abstract-having node (the spec 031 FR-005 fallback case), **When** `h-read-node` is invoked with default `contentScope`, **Then** the meta block contains `Source: abstract-fallback` but NOT `Source: abstract-stale` — there's no content to be stale against.
6. **Given** a node with both `Source: abstract-stale` AND `Source: abstract-fallback` would theoretically apply (a node whose content was once set and is now null but abstract remains): this case is **excluded by FR-007** — when content goes to null, `abstractOriginHash` is left as-is, but the staleness check requires content to be non-null, so the stale marker does not fire. Only the fallback marker applies.

### User Story 3 — `h-validate` flags stale abstracts as a warning (Priority: P3)

`h-validate`'s existing per-node checks (broken edges, sparse nodes) gain a third check: stale abstracts. When a node satisfies the staleness condition (per US2), the validator reports `[stale-abstract] <urn> — abstract may not reflect current content`. The check is a **warning**, not a hard failure — staleness is a quality signal, not an invariant violation. The validator's existing "Found N issue(s) in M nodes" envelope counts stale-abstract warnings alongside other issues.

**Why this priority**: Bulk-detection across a memory. A human or agent running `h-validate` periodically (or as part of pre-commit / CI gates) gets a list of stale abstracts to refresh. Useful but not on the critical path for the RAG follow-up (which reads `abstractOriginHash` directly, not via `h-validate`).

**Independent Test**: Seed a memory with three nodes: one fresh-abstract, one stale-abstract, one no-abstract. Run `h-validate`. Assert the stale node appears in the issue list with the `[stale-abstract]` tag; the other two do not.

**Acceptance Scenarios**:

1. **Given** a memory containing a stale node, **When** `h-validate` is invoked, **Then** the report includes a line `[stale-abstract] <urn> — abstract may not reflect current content`.
2. **Given** a memory containing only fresh-abstract or no-abstract nodes, **When** `h-validate` is invoked, **Then** no `[stale-abstract]` lines appear.
3. **Given** a memory containing a mix of stale, fresh, and sparse nodes, **When** `h-validate` is invoked, **Then** the issue count reflects the sum across all three rule types; each issue type uses its own tag (`[stale-abstract]`, `[sparse]`, `[broken-ref]`).

### Edge Cases

- **No abstract, any content**: `abstractOriginHash` is `null`. Staleness check short-circuits (one side is null → not stale). No marker, no warning.
- **Abstract set, content null** (FR-005 fallback case): `abstractOriginHash` is `null`. Staleness check short-circuits. `Source: abstract-fallback` may fire on read; `Source: abstract-stale` does not.
- **Both null** (sparse node): all hashes are null. No staleness signal. The sparse-node check from spec 031 FR-011 handles this case independently.
- **Content updated to null after abstract was authored**: per FR-007, `abstractOriginHash` is left untouched on a content-only write. So the stored hash persists. But the staleness check requires `content IS NOT NULL` to fire — so the marker does not appear. The result: a "ghost" hash sits in the DB. Cosmetic; no consumer surfaces it. Could be cleaned up by a future spec, not in scope here.
- **Hash collision** (two different content values yielding the same hash): 8 hex chars = 32 bits of fingerprint. Birthday-bound collisions become probable around `2^16 ≈ 65,000` distinct content versions; a memory whose nodes turn over content frequently could hit a coincidence collision in the lifetime of the deployment. **Failure mode**: one stale abstract is treated as fresh → vectorised by the RAG follow-up → one misleading embedding in the index. Not catastrophic (worst case: one wrong retrieval, recoverable by manual abstract refresh). Acceptable risk for the v1 use case; the RAG spec needs to budget for "some embeddings in the index are stale" anyway because of timing windows between content edit and abstract refresh. If a future deployment shows this is a real problem, widening the hash to 16 hex chars (64 bits) takes collision probability to `2^32 ≈ 4 billion` content versions — comfortably out of reach. Migration is the obvious follow-up if/when needed.
- **`abstract` is set to an empty / whitespace-only string** (per spec 031 FR-009, this normalises to `null`): `abstractOriginHash` is cleared along with `abstract` per FR-006. No staleness signal.
- **Restore an older version where `abstractOriginHash` is null but the version's content + abstract are both non-null** (e.g., a version snapshotted *before* this spec ships, then restored *after*): the restored node has both columns populated and `abstractOriginHash` null. **Since #1128 this ARMS the marker, and that is correct** — the restored abstract genuinely has never been checked against the restored body, which is exactly what the marker says. *(Before #1128 this bullet promised the opposite: the check short-circuited on the null and stayed silent. That was the guard's cost, not a feature.)* **Decision (plan D4) is unchanged**: `restoreNodeVersion` writes `version.abstractOriginHash` verbatim — no recomputation from restored content — preserving the "restore = byte-identical to the version" invariant. Only the consequence moved. An operator who has checked the restored abstract against the restored body clears the marker the same way as anywhere else: re-save the abstract, or assert `abstractStillAccurate`. Pinned by `#1128 — a RESTORE of that revision arms the marker on the live node` in `server.nodeAbstractStaleness.test.ts`, which performs the restore and asserts the marker. *(The neighbouring `#1128 — restoring a revision with a null hash arms the marker` pins only the PRECONDITION — that a revision captured the null — and never restores; @codex caught this citation naming it, PR #1139.)*

## Requirements

### Functional Requirements

- **FR-001**: `Node` MUST gain an optional `abstractOriginHash` text column. Existing rows backfill to `NULL`. The column is additive — no existing column changes shape or semantics.
- **FR-002**: `NodeVersion` MUST gain a matching optional `abstractOriginHash` column so version-history snapshots capture the hash alongside the abstract (per the spec 031 lesson learned: NodeVersion is a curated subset; new Node columns require matching NodeVersion additions or restore silently drops them).
- **FR-003**: On any write surface that sets or replaces `abstract` to a non-null value (`h-add-node`, `h-update-node`, GraphQL `upsertNode`, importer), the system MUST set `abstractOriginHash` to `hash(current content)`. If `content` is null/empty at write time, `abstractOriginHash` MUST be set to `null`.
- **FR-004**: On a write that updates ONLY `content` (no `abstract` key in the payload), the system MUST leave `abstractOriginHash` untouched. The stored hash will diverge from the new `contentHash`, producing the staleness signal on the next read.
- **FR-005**: On a write that updates BOTH `abstract` and `content` together, the system MUST set `abstractOriginHash` to `hash(new content)`. The author is affirming both writes match.
- **FR-006**: On a write that clears `abstract` (`abstract: null`), the system MUST also clear `abstractOriginHash` to `null`. No abstract means no staleness signal to maintain.
- **FR-007**: On a write that clears `content` (`content: null`) without an abstract update, the system MUST leave `abstractOriginHash` untouched. The staleness check downstream requires `content IS NOT NULL` to fire, so the "ghost" hash does not produce false positives. (This is the deliberate edge-case handling for the abstract-only-archive case.)
- **FR-008**: The hash algorithm used for `abstractOriginHash` MUST be SHA-256 of the **plaintext content**, truncated to the first 8 hex characters. A shared helper `computeContentHash(content: string | null) → string | null` (per plan D3) MUST be the **single write-side definition** used across every surface that maintains `abstractOriginHash` (MCP h-add-node / h-update-node, GraphQL upsertNode, importer). The same helper MUST be used at read time by `h-read-node` and `h-validate` to compute the comparison value (see FR-010 / FR-011). The hash is byte-equal across writers and readers because they all call the same function.
  - **Existing `Node.contentHash` semantics are NOT changed by this spec**: that column's documented domain (`SHA256(yaml+md)[0:8]` per the schema doc, set by external YAML / Git-sync producers) is preserved as-is. The staleness check compares `abstractOriginHash` against `computeContentHash(node.content)` — computed at read time, NEVER against the stored `contentHash` column. This avoids redefining `contentHash` semantics under existing consumers (PR-207 review item 1).
- **FR-009**: The hash MUST be computed over **plaintext** content, never encrypted ciphertext. Behaviour by surface:
  - **GraphQL `upsertNode`**: the resolver's existing decrypt-pre-write pattern surfaces plaintext content before encryption runs; `computeContentHash` slots in there. Works correctly on encrypted memories.
  - **MCP `h-add-node` / `h-update-node`** *(rewritten — spec 041 changed this; @copilot, PR #1139)*: as drafted, these handlers did not invoke the encryption envelope at all, so content sat plaintext on the row despite `Memory.isEncrypted = true` and the hash worked by accident of that asymmetry. **Spec 041 PR-2 closed that hole**: the update path now decrypts `existing` with the session key before computing the hash, and encrypts `content` / `abstract` / `data` before persisting — or REJECTS the write when the memory is locked. `computeContentHash` still sees plaintext, but now by construction rather than by omission, and the ordering (decrypt → hash → encrypt) is load-bearing rather than incidental.
  - **Scope**: this spec's staleness signal works correctly on the existing surface as it is today. The **MCP encryption-parity follow-up** referred to here as pending has since shipped (spec 041, closing #206), exactly as predicted: the MCP handlers gained the decrypt-existing-content-on-update step alongside encrypt-on-write, and the hash-maintenance machinery needed no change — only the decrypt-then-hash ordering moved.
  - **What this spec does NOT do** *(historical - @codex, PR #1139)*: it did NOT add MCP-side encryption, and it did NOT scope-restrict the feature to non-encrypted memories. **The first half is no longer a description of the system**: spec 041 added MCP-side encryption, so encrypted-memory staleness no longer works *because the MCP layer stores plaintext on the row* - it works because the handler decrypts before hashing. An implementer must follow the bullet above, not this one. Kept rather than deleted because it records what this spec's scope was, and dropping it would hide that the plaintext-on-row behaviour ever existed.
- **FR-010** *(rule changed by [#1128](https://github.com/hadron-memory/hadron-server/issues/1128), PR #1129 `abdc6a8`)*: `h-read-node` MUST emit a `Source: abstract-stale` line in the meta block when ALL of the following are true:
  - (a) `node.abstract IS NOT NULL` AND non-empty
  - (b) `node.content IS NOT NULL` AND non-empty
  - (c) `node.abstractOriginHash !== computeContentHash(node.content)` — which is true when the fingerprint **disagrees** with the content and equally when it is **absent** (hash domains match because both sides use the same helper)
  - (d) the response includes the abstract (`contentScope` is `'abstract'` or `'all'`)

  The condition is **unverified**, not merely *changed*: a missing fingerprint is not a free pass. An abstract with no fingerprint has never been checked against the body it claims to summarise, and that is the same thing the marker exists to say.

  **This deliberately reverses PR-207 review item 5.** That review required (c) to be an explicit `!= null` check *precisely so* `null !== "abc12345"` could not fire the marker — correct then, wrong now. The guard's premise was that every row predated the column and would fire at once; that premise drained (see below), and the guard's cost was the reverse: FR-007 gives a null hash to an abstract written before its body, a later content-only update preserves that null, and the guard then read the null as *"nothing to check"*. **The one write ordering most likely to produce a mismatched abstract — summary first, body afterwards — was the only ordering that raised no signal**, and a missing marker was indistinguishable from a verified one.

  **Why arming is safe, and what would make it unsafe again.** The justification is a population measurement, so it carries an expiry. Live nodes with both an abstract and a body, and no fingerprint: **2 of 1024** (2026-09-03), **2 of 1027** (2026-09-04) — the *same* two rows (`cor:api:150`, `findings:unscoped-loc-lookup-crosses-memories`), untouched since July, while the corpus grew 54 nodes. A static residue, not a shrinking backlog. **What invalidates this**: anything that refills that population — a bulk import writing abstracts without bodies, a restore-heavy workflow replaying pre-fingerprint snapshots, or a write path that stops re-stamping the hash. Re-measure before assuming it still holds.

  The marker MUST be positioned consistently with the existing `Source: abstract-fallback` marker (same meta-block slot, same prefix format). The marker MUST NOT appear under `contentScope: 'content'` (the abstract isn't in the response; the marker would alarm without reason).

  **One marker string, deliberately.** The reader's action is identical for a disagreeing and an absent fingerprint — open both and compare — so `abstract-stale` keeps its meaning of *"do not trust this abstract until you have checked it"* and gains no competing vocabulary for clients to learn. Only the described condition moved.

  **One home for the predicate**: `isAbstractUnverified` in `src/lib/contentHash.ts`, shared by `h-read-node`, `hadron_find_nodes`, and `h-validate`. Two copies of a rule stay in step only until someone edits one.

  **Encryption — the v1 gate has LIFTED on this surface.** As drafted, the predicate short-circuited whenever `memory.isEncrypted` was true, because the MCP read path did not decrypt and `computeContentHash(ciphertext)` would false-positive on every node. That was the safe v1 posture (PR-210 review) pending the encryption-parity follow-up. **That follow-up shipped** — spec 041 PR-2, closing [#206](https://github.com/hadron-memory/hadron-server/issues/206) — and `mcpDecryptOrMark` now decrypts when the session holds the memory's key, flipping the projection's `isEncrypted` to false. So the predicate runs on plaintext and **the marker DOES fire on an encrypted memory while it is unlocked**; a locked memory still emits nothing, and its silence says nothing either way. Verified against `src/mcp/server.ts` rather than inherited from this paragraph's previous wording. **`h-validate` is the exception and keeps the v1 gate — see FR-011.**
- **FR-011**: `h-validate` MUST flag stale abstracts as a warning. Predicate matches FR-010 conditions (a)–(c) above (the `contentScope` gate, FR-010 (d), doesn't apply at validation time — h-validate considers every node uniformly). Since #1128 this is not merely a matching predicate but the SAME function, `isAbstractUnverified`. Issue format: `[stale-abstract] <urn> — abstract may not reflect current content`. Stale-abstract warnings MUST be counted in the existing issue total alongside sparse-node and broken-edge warnings; the consumer-facing report shape is unchanged (one issue list, one summary count). **Encryption: h-validate KEEPS the v1 gate, and no longer shares FR-010's.** It computes `checkStale = !memory.isEncrypted` from the memory row directly and never decrypts, so the check is skipped on an encrypted memory whether or not a session holds the key. FR-010's gate lifted when spec 041 PR-2 gave the READ path a decrypt step; this surface got no equivalent, so the two are now deliberately different and each states its own rule rather than one deferring to the other.
- **FR-012**: GraphQL `Node` type MUST expose `abstractOriginHash: String` as a read-only field. The field MUST NOT appear on `NodeInput` — `abstractOriginHash` is system-managed, never settable by a caller. (Allowing caller-supplied values would defeat the staleness invariant: a malicious or buggy caller could write a fresh-looking hash that doesn't match the content.) **Implementation-level invariant** (per PR-207 review item additional-2): every server-side write to `nodes.abstract_origin_hash` MUST flow through the `computeContentHash` helper. A test asserting that the helper is the only caller of `Prisma.NodeUncheckedCreateInput.abstractOriginHash` / `Prisma.NodeUncheckedUpdateInput.abstractOriginHash` (or an equivalent grep gate) pins this.
- **FR-013**: The node.yaml importer MUST treat YAML files without an `abstractOriginHash:` frontmatter key as a fresh authored write (compute `abstractOriginHash` from the imported content at parse time, via `computeContentHash(content)`). When the YAML carries an `abstractOriginHash:` key, the importer **validates** it against `computeContentHash(content)`: if they agree, accept the YAML value (round-trip preserved); if they disagree, the YAML claims the abstract is stale relative to the imported content — accept the YAML value but emit a warning during import (the YAML was authored externally; trust the producer but surface the disagreement). This middle-ground design preserves round-trip integrity for legitimately-stale exports while making tampered imports observable in the sync log (PR-207 review item additional-1). The exporter MUST write `abstractOriginHash:` to the frontmatter when the column is non-null (omit when null, parallel to the spec 031 importer/exporter omit-on-null convention).

### Entity Impact

**Modified**:

- **Node** (`prisma/schema.prisma`) — adds an optional text column `abstractOriginHash` positioned adjacent to the existing `contentHash` field in the model layout. Nullable; no default; no CHECK constraint. Same column width / type as `contentHash`. Existing rows backfill to `NULL` (no staleness signal on pre-spec nodes — they were authored before the invariant existed; treating them as "always fresh" is the right migration default).
  - **Superseded in part by #1128 (@codex, PR #1139)**: the backfill itself is unchanged - existing rows still get `NULL` - but *no staleness signal on pre-spec nodes* no longer follows from it. A `NULL` on a row that has BOTH an abstract and a body now emits the marker, because a fingerprint that was never taken is not evidence the abstract was ever checked. Pre-spec nodes are no longer treated as always-fresh; see FR-010.
- **NodeVersion** (`prisma/schema.prisma`) — adds the matching optional text column `abstractOriginHash` so audit snapshots and `restoreNodeVersion` round-trip the hash alongside the abstract. Same lesson learned as spec 031's FR-013 / Entity Impact note — NodeVersion is a curated subset, not auto-projected. The migration MUST add the column AND every `nodeVersion.create` call site MUST include it AND `restoreNodeVersion`'s write payload MUST include it.

**Source of truth**: `hadron-server/prisma/schema.prisma` (Prisma schema + migration tracked in tasks.md).

## Success Criteria

### Measurable Outcomes

- **SC-001**: Write-path round-trip invariant holds. An integration test seeds a node through every write surface (`h-add-node`, `h-update-node`, GraphQL `upsertNode`, importer) and asserts `abstractOriginHash` matches `hash(content)` after every fresh write — across at least 5 distinct seed scenarios covering the FR-003 through FR-007 cases.
- **SC-002**: Staleness signal is observable by readers. After a content-only update, the next `h-read-node` with `contentScope: 'all'` returns a response containing `Source: abstract-stale` in the meta block. Refreshing the abstract clears the marker on the subsequent read. Demonstrated by a regression test.
- **SC-003**: `h-validate` reports stale-abstract warnings accurately. A seeded memory containing N stale, M fresh, and K abstract-less nodes produces exactly N `[stale-abstract]` warnings in the validator's report and zero false positives. Demonstrated by a regression test.
- **SC-004** *(superseded by #1128 — recorded, not deleted, because it was a shipped criterion)*: **As shipped**, zero behaviour change for any pre-spec node: the check short-circuited on a null `abstractOriginHash`, so no marker appeared on legacy nodes. **Since #1128** that is deliberately no longer true — a pre-spec node holding both an abstract and a body now DOES show the marker, because a fingerprint that was never taken is not evidence the abstract was ever checked. The criterion that replaces it: the marker MUST NOT appear on a node missing either text (no abstract to doubt, or no body to doubt it against), and the population it newly arms on MUST stay negligible — measured at 2 rows of 1024, with the expiry condition stated in FR-010.
- **SC-005**: GraphQL exposure is read-only AND every server-side write to `abstractOriginHash` flows through `computeContentHash`. Two assertions:
  - **Schema-level**: a GraphQL contract test asserts `NodeInput.abstractOriginHash` is absent from the input type (introspection-based).
  - **Implementation-level**: a CI grep gate (or static unit test) asserts that `computeContentHash` is the only function whose return value flows into `Prisma.Node*Input.abstractOriginHash`. Pins FR-012's invariant — no future contributor can sneak in a caller-supplied or hand-computed value.
- **SC-006**: Importer round-trip preserves staleness. A node exported with a stale `abstractOriginHash` (hash differs from content), re-imported via YAML round-trip, retains the same `abstractOriginHash` — the importer accepts the YAML value when it disagrees with the computed value (per FR-013 middle-ground design), emitting a warning in the sync log. Verified by a round-trip integration test plus a "tampered hash" test that confirms the warning fires.

## Assumptions

- **Hash algorithm matches `Node.contentHash`'s SHA-256[0:8] width** but is a NEW server-side helper (`computeContentHash`). No new crypto primitives. The existing `Node.contentHash` column is set by external producers (YAML frontmatter via importer, Git sync) and documents its domain as `SHA256(yaml+md)[0:8]`; this spec does NOT modify that domain or those producers. The staleness check compares `abstractOriginHash` against `computeContentHash(node.content)` (computed at read time), NOT against the stored `Node.contentHash` column — so the two columns serve different purposes and stay in their own lanes. Collision risk is quantified in Edge Cases above.
- **Branch number `199` vs spec directory number `032` divergence is acceptable.** The speckit feature-branch script picked `199` because of an unrelated `198-ensure-agent-subscription-race` branch. The canonical spec-directory sequence (`specs/NNN-name/`) continues with `032`. Future readers should treat the spec-dir number as authoritative; the branch number is a build artefact.
- **Passive observation, not active correction.** The system observes staleness and reports it; it does NOT automatically rewrite or invalidate the abstract. The author (human or agent) remains responsible for refreshing stale abstracts. A future spec could add an automated "refresh stale abstracts" surface, but it's out of scope here.
- **Encryption interaction follows spec 031's lesson.** The hash is computed over plaintext content BEFORE the encryption envelope is applied. The hash itself is non-sensitive (8-char fingerprint, not the content) and stored plaintext in `Node.abstractOriginHash` regardless of `Memory.isEncrypted`. Documented explicitly in FR-009 because the existing encryption surface in `src/lib/nodeCrypto.ts` only knows about content/data/abstract — hash maintenance is a resolver-level concern, not an encryption-layer concern.
- **`h-find-nodes` preview annotation is out of scope.** Adding a stale-abstract annotation to find-nodes previews would add visual noise to the survey/triage surface (callers are already triaging; adding a "this might be wrong" annotation per hit competes for attention with the actual hit content). A follow-up spec could add it if the RAG layer's behaviour proves to need a preview-level signal. For now, US2's `h-read-node` marker is the only end-user surface for the signal; US3's `h-validate` is the bulk surface; the RAG follow-up consumes the column directly.
- **`abstractOriginHash` is system-managed only.** The GraphQL surface exposes it read-only; MCP write surfaces don't accept it as an input parameter. Callers cannot supply a hash directly. Trade-off: a future migration tool that needs to bulk-fix stale hashes would need a separate (privileged) administrative path. Out of scope for v1.
- **Backfill on existing nodes is intentionally absent.** Existing nodes have `abstractOriginHash IS NULL` and produce no staleness signal. The "always fresh" default is correct for pre-spec content: those abstracts were authored before the invariant existed, so we have no truthful hash to attribute. Operators wanting to bulk-mark pre-spec nodes as "needs review" can run a one-off SQL update (assigning the current `contentHash` to `abstractOriginHash` would mark all existing abstracts as freshly authored — which is also defensible). Either policy is fine; the default is no signal.
- **Target repository is `hadron-server` only.** Schema, MCP tools, GraphQL surface, importer/exporter, validator. Portal-side UI rendering of the staleness signal is a follow-up if it requires non-trivial UX work; once the API returns the marker / signal, portal rendering is a localized component change.
